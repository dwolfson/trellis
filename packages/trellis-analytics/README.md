# trellis-analytics (Analytic Library)

Routines and steps with a result envelope, discovered through the
`trellis.analytics` entry point. Pieces 2a (library) and 2b (the
`curation_coverage` routine) of `docs/extensibility-walking-skeleton-brief.md`.

- `trellis_analytics.envelope`: `Envelope` and the four states.
- `trellis_analytics.manifest`: `RoutineManifest` / `StepManifest`, subclasses of
  pyegeria's `AnalyticFunctionSpec` carrying the five additive fields themselves.
- `trellis_analytics.discovery`: `discover()` and `register()` (into pyegeria's registry).
- `trellis_analytics.readers.ods`: read-only access to RE's registry (SQLite file or Postgres).
- `trellis_analytics.routines.curation_coverage`: published / not yet / blocked.

- `trellis_analytics.routines.context_pack`: `context_pack(reader, subject, consumer_kind, identity)`, the first context
  pack (P12 build step 1): reads Egeria only through `readers.egeria.PackReader` (`EgeriaPackReader` is the real one),
  returns a tabular shape, a document shape and a manifest; every fact has a state word and provenance, and a fact RE
  holds but never published (`ReHeld`, names only) reads "not published", never a value. `answer_scoring` is the P12
  rubric. The measurement notebook is `docs/experiments/p12-context-pack-coco-pharma.ipynb`.
- `trellis_analytics.portal`: host 3, the Portal tile. `curation_coverage_tile` reshapes the routine's result (no
  computing of its own) and `report_specs()` is the tile's `FormatSet`; load it with
  `PYEGERIA_REPORT_SPEC_MODULES=trellis_analytics.portal:report_specs`.
- `examples/`: host 1 `curation_coverage.py`, host 2 `curation_coverage.ipynb` (papermill: `slug`, `ods_url`),
  and `curation_coverage_tile.md`, the tile's spec as a Dr.Egeria report-spec document (the Advisor's parser reads it to
  the same `FormatSet`).

- `trellis_analytics.step`: `SurveyStep`, level 2 of a step (brief 2c'): declared inputs only, never a password,
  read-only on the resource at most, the envelope on every result, the host's store.
- `trellis_analytics.declare`: `manifest_properties`, what a step's Egeria declaration says about it, from its
  manifest. The declaration is Resource Explorer's engine host's (a SurveyActionService, its SupportedGovernanceService
  link with the manifest's `request_type`, and a GovernanceActionType with a GovernanceActionExecutor), generated by
  `packages/resource-explorer/scripts/generate_engine_host_declaration.py` into
  `docs/dr-egeria/engine-host/library/<step>.md`. Never run here.
- `examples/steps/database_staleness/`: piece 2c, a user step as its own installable package (`run(inputs)` plus
  a `StepManifest` entry point). Resource Explorer runs it through `survey_step_host`, from a survey or when Egeria
  dispatches request type `re-database-staleness` to RE's engine host; its catalog entry comes from
  `generate_external_step_entries.py` and its Egeria declaration from `generate_engine_host_declaration.py` (both in
  `packages/resource-explorer/scripts/`).

No executor: a routine is called directly; a step is run by a host.

**What a step can and cannot reach (Resource Explorer's host).** A step is in-process, trusted code. The host
enforces three things: it hands no connection to the resource (a step declaring `connection` is refused); `inputs.ods`
is a read-only reader of RE's stored rows exposing only its SELECT methods (`query`, `row_count_snapshots`, ...): each
query must be one plain SELECT, and runs in a separate thread on a connection that cannot write (a rolled-back READ ONLY
transaction on Postgres; read-only mode, `query_only` and a read-only authorizer on SQLite), so the step holds no
connection, registry object or database URL; and the step's code runs with no Egeria identity, so it cannot act in Egeria
(the host publishes its results afterwards, as itself). This narrows what a step is handed; it is **not a sandbox**.
Python code in the same process can reach past any of it on purpose, so install only steps you would run as Resource
Explorer itself.

**Making a step Egeria can dispatch.** Declare `request_type` (default `re-<name>`) and `nothing_to_derive_guard`
(one of `survey-completed`, `survey-invalid`, `survey-failed`; applied when none of the step's results is `measured`
or `nothing_found`) in its `StepManifest`; install it where RE's worker runs; generate its declaration with
`generate_engine_host_declaration.py`; and have the owner run `engine-host/library/<step>.md`. A step may not take a
built-in RE step's name or request type, must not declare `connection`, and must emit `ResourceMeasureAnnotation`.

```python
from trellis_analytics.readers.ods import OdsReader
from trellis_analytics.routines import curation_coverage
r = curation_coverage(OdsReader("postgresql://..."), "database", "coco_pharma")
print(r.envelope.result_state, r.to_dict())
```
