The DRAFT badge where it lives, and the blank my own ask created

Both round-2 items were fixed properly, and the n_distinct fix went further than I asked — three corrections deep, catching the reltuples provenance and the PG13 sentinel ambiguity I had not seen. This page is about what the fixes left behind, which in one case is a direct consequence of the correction itself.

One · the badge, in classic, as shipped
DataClassMatch (4)
• public.patient.email: matches Data Class “Email Address” — 1,000 of 1,000 sampled values conform (sample: 1,000 rows, seed 42) [92]
• public.patient.national_id: no Data Class matched, but 998 of 1,000 sampled values share one pattern — a candidate class [64] draft

This is right, and one part of it is right in a way worth naming. The badge is drawn only for a non-empty contentStatus, and index.html:6660 says why: an empty value is not stated, which is not the same as confirmed, so it must not earn a badge of its own. That is the measured-zero-versus-nothing-found rule applied without being asked.

And the reason the other three rows survive having no badge is that describe() already puts the verdict in words — not established — … This is not a statement that no match exists. The badge is a second channel on a distinction the sentence already carries, which is the right order for those two to be built in.

Two · what /next does with it — and the decision waiting there

/next has no live-Egeria annotation surface at all: no content_status, no egeria-surveys, nowhere. So the badge is not missing from a screen that shows annotations — the screen does not exist yet.

By RULING-CLASSIC-AND-NEXT.md that is permitted: capability may diverge. It is not the silent-omission case, because nothing on /next currently renders a proposal as though it were a finding. But it becomes that case on the day that pane is built, so the rule is worth stating before then rather than after:

/next's annotation pane ships with the status mark on day one, or it does not ship. A pane that lists proposals and findings in one list with nothing separating them is the exact defect slice 10 was built to remove, rebuilt one surface over.

and it cannot be amber there

Classic's amber (bg-amber-500/20 text-amber-400) is right for classic's slate chrome. It cannot port: /next has three audited state roles — ok, warn, gap — and the audit already records that state-warn and gold sit within 1.02:1. There is no room for a fourth.

There does not need to be one. DRAFT is not a state. ok/warn/gap say what we found out; DRAFT says who has agreed to it so far, which is the same axis as measured / declared and is orthogonal to all three. A near-unique national-id column can be a warn and a draft at once. So it is drawn as a mark in ink, not a colour:

public.patient.national_id draft
no Data Class matched, but 998 of 1,000 sampled values share one pattern — a candidate class
■ sensitive pattern · confidence 64 · accept as declared ›

The state colour stays available for the finding; the chip carries the agreement. Both read at a glance, and neither needs the other's channel.

Every other field is real. The row is labelled measured. And the one blank has no explanation anywhere, because the reason was known at survey time and not written down.

This one is mine. I asked for the sign to be fixed; _resolve_n_distinct fixes it by correctly refusing to guess — it returns None rather than a confident wrong number. But it returns None for four different reasons, and the row is still written with state = measured, because every other pg_stats field came back fine. Row-level state cannot carry a per-field absence. So a wrong number became a blank that cannot say why, which is the same rule one step along: absence and failure are states, never blanks.

And there is a live case that produces it on a healthy database. ever_analyzed is derived from pg_stat_user_tables.last_analyze — which pg_stat_reset() clears, while the pg_stats rows survive it untouched. After a stats reset, every column whose n_distinct is a negative ratio — which is every near-unique column: every id, every email, every key — silently loses its distinct count, on a database whose statistics are perfectly good.

stats_reset is already in scope (database_surveyor.py:379), from the get_stats_reset() that round 1 asked for — to tell a real rate from a counter reset. It turns out to answer this question too, and this path does not consult it.

the four, and what the card should say
n_distinct is null
“not collected for this column — run ANALYZE ›”
reltuples < 0 (PG14+)
“the table has never been ANALYZEd — run ANALYZE ›”
reltuples = 0, never analyzed
same sentence — and on PG13 this is the ambiguous one, which is why the sentence must not say “empty”
reltuples = 0, stats were reset
“distinct count not resolvable — table statistics were reset 2026-09-19; the other figures predate the reset and stand” — and no ANALYZE is offered, because ANALYZE is not the problem

Three of the four end in the same action and one ends in no action at all, which is the whole reason they cannot share a dash. Cheapest shape: a short reason string beside the value, the way state already sits beside the row.

Four · the exposure heatmap — wait, and do not ship it caveated

Wait. Not because the drawing is hard, but because the next drawing is blocked on a build decision rather than on a design one. The two candidate fixes produce different pictures: column_privileges yields grants with a grantor and a grantee, so a cell can say granted directly versus inherited via readers and the revoke path is drawable; has_column_privilege() yields a boolean per pair with no path at all. The popover I sketched on page 10 exists under one and not the other. Drawing it now means drawing it twice.

But one thing is worth settling now, because it is a shipping rule rather than a drawing. Until those reads land, the heatmap should not ship at all — not behind a caveat, not in a preview, not with a banner. A caveated exposure grid is still read as a grid: the reader's eye takes the empty cells as the answer and the sentence above them as boilerplate. Everywhere else in this product a caveat is the honest move. Here it is not enough, because the failure is silent and points the wrong way.

The three gaps are logged at Backlog.md:6532 as slice #10 follow-ups and are not built. Page 10 stands as the target; it is not a build-ready spec until they are.
