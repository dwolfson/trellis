Correction first

Ports are not derived from the accepted set

The Curate column says “ports and wires are derived from the accepted components' interfaces and relationships”. They are not. They are derived at survey time, from deployment artifacts only — Dockerfile EXPOSE, compose ports/depends_on, OpenAPI, .proto, GraphQL, FastAPI route markers — and attached to a component by longest path-prefix match. Acceptance is not consulted anywhere in interfaces.propose(). Rejecting a component leaves its port rows untouched.

What acceptance does change is which ports get drawn: the diagram is rendered fresh on every read, drops rejected components, and drops any port whose owner is not a shown node — reporting the count in its caption rather than attaching it to a guess. That is display, not derivation, and the sentence claims the stronger thing.

Three ways out, and the ruling
Fix the sentence
now

“ports and wires are read from the repository's deployment artifacts; the diagram shows those belonging to accepted components”. One line, and it is true today.

This is the one that ships. A column asserting a derivation the code does not perform is the same defect class as the inventory counting vendored files — and it is in the sentence a curator reads to decide whether to trust the column.

Adopt on accept
the destination

Accepting a component adopts its declared ports — they become curated facts with the acceptance's author and date, written to architecture_materialized_ports, which exists and which nothing writes today. The materializer exists too, and has no caller.

Blocked, and not by us: SolutionPort creation is a generic-metadata workaround for pyegeria ISSUE-85, and wires cannot be published at all — the outbox has no creator for them, and SolutionLinkingWire relationships carry no qualifiedName, so the outbox's idempotency cannot cover a retry. That was measured and deliberately deferred on 2026-09-03. It stays deferred, and stays named.

Give ports a verdict
no

A port is not a proposal about the world; it is a line in a Dockerfile. There is nothing for a person to agree or disagree with, which is exactly what the classic UI already says: read-only, no verdict to give.

If a declared port is wrong, the repository is wrong, and the fix is a pull request rather than a verdict. Keep the asymmetry: components are proposals, ports are readings.

And the thing that decides the whole shape

On most repositories there are almost no ports and no wires at all. Ports exist “essentially not at all” for logical components; Prometheus, one of the better cases, has 1 port and 0 wires. A dedicated ports-and-wires screen would be an empty room on nearly every resource — and an emptiness that holds everywhere is a bug report about the reader, not a finding about the corpus.

So ports are a column on the component, not a screen: two words on the row where they exist, nothing where they do not, and one honest sentence at the foot of the tree when a repository declares none.

No declared topology — egeria-python declares no ports and no wires. Ports are read from Dockerfiles, compose files and API documents; this repository has none of those with an exposed interface.

That sentence says what it looked in, so a reader can tell “nothing declared” from “nobody looked”. Which is the whole difference between ∅ and ?, on the one surface where the emptiness is the normal case.

It is already verdict-aware: rendered fresh on every read, rejected components dropped, accepted solid, undecided dashed, a rejected blueprint ungrouping its members. Nothing needs building for it to respond to the tree — accept a branch and the next read redraws.

What it is not is the acting surface. It comes back from Kroki as a finished SVG, so nodes are not controls without a mapping layer nobody has asked for. Reading and acting side by side, on paper, in the diagram font — the one place the type system is deliberately overridden.

Two ceilings it carries and must keep saying out loud: 50,000 characters, reported and never truncated, and 20 classed nodes — past which some pending nodes lose their dashes, on the stated grounds that losing the styling beats losing the diagram. On a 609-component repository both bite, so the tree is the surface that scales and the diagram is the one that explains.

What this round does not touch. The two perspectives (detect and coupling) propose different component sets and are never merged, while a verdict is keyed by scope and therefore lands on both. That is a real ambiguity and it needs its own round — naming it here so it is not mistaken for settled.
