# Survey tab unification — real survey types, one publish action, batched execution

**Status: implemented, tested, and live-verified this session (D1-D5 all shipped). Not yet committed.**

## Context

Live use of Scouting's Survey tab surfaced that "combine the previous screens onto one tab" had produced something more confusing than either predecessor screen: the tab showed a hardcoded "Run Scouting Scan" button and a hardcoded "Refresh coarse profile" card (with its own checkbox and its own "Publish this phase's findings" button) side by side with the generic Survey Definition candidate panel underneath — meaning the exact same two surveys (the scouting scan, the coarse profile) were reachable two different ways, with two different action vocabularies, and the generic panel's own candidates for those same two surveys were an unexplained duplicate. Four concrete problems were raised in one pass:

1. The scouting scan and coarse profile weren't showing up **as** Survey Definition types in the generic candidate list — they'd been special-cased instead of authored as real Survey Definitions the way "Repo Full Survey" already was.
2. Publishing had a different button, different label, and different scoped-steps list per survey type instead of one consistent action.
3. Naming: "Repo Coarse Scout" read as a git-statistics pass, not obviously "Scouting." A rename to "Git Statistics Survey" (and a new "Coarse Profile Survey") was proposed.
4. The scouting scan had visible results; Coarse Profile's own results (file/language classification, data profiling) weren't showing anywhere in the Results tab.

Investigating (4) turned up something not purely cosmetic: `SurveyDefinitionExecutor.run()` dispatched every step of a Survey Definition **one at a time**, each instantiating its own fresh `SurveyOrchestrator.run(steps=[key])` call. A pre-existing shared-resource dedup (`trellis_microflow.resolve_resources`, e.g. "don't download the repo zipball twice") only ever deduped *within* one `SurveyOrchestrator.run()` call — so a 4-step "Coarse Profile" survey dispatched through the generic executor would download the same zipball four times, once per step, silently. This made authoring a real multi-step Coarse Profile Survey Definition a real backend fix, not just a UI relabeling exercise.

## Decisions

**D1 — Batch the executor's per-step dispatch.** `ResourceTypeAdapter` gains an optional `run_batch: Callable | None = None` field: `(entity, registry, re_analysis_step_keys: list[str], **kwargs) -> {"annotations": [...], "errors": [...]}`. The executor's dispatch loop in `SurveyDefinitionExecutor.run()` groups consecutive `executes_at="resource-explorer"` steps (not prefect-routed, all recognized by the adapter) and calls `run_batch` once with the whole step-key list when the adapter provides it, instead of once per step. A group of exactly 1 step falls through to the original per-step path unchanged. Adapters that don't opt in (database, filesystem, and pre-D1 test fakes) default to `None`, preserving prior behavior byte-for-byte. `repo_survey_definition_adapter.py` gains `_run_batch(project, registry, step_keys, fast=False, **_) -> dict`, which does exactly one `SurveyOrchestrator.run(steps=step_keys)` call — the existing D6 shared-resource dedup then applies across the whole group for free, since it was always scoped to one orchestrator run, just never previously given more than one step at a time to work with. Batched steps share one `"ok"`/`"error"` status in `steps_report` (accepted simplification — attributing an error to one specific step_key inside a batch would mean instantiating each surveyor just to read its `step_name`; the real error text is still fully surfaced in `errors` and each step's `detail` field, just not pinpointed to a single step).

**D2 — Author "Coarse Profile Survey" as a real 4-step Survey Definition.** `repo_language → repo_file_classification → repo_file_structure → repo_data_profiling`, chained via Dr.Egeria (`docs/dr-egeria/repo-survey-definition-coarse-profile.md`, generated from `docs/dr-egeria/repo_survey_types.csv` by `scripts/generate_repo_survey_definition.py`). This directly closes complaint (4): once this is a real Survey Definition with a `run_batch`-capable adapter behind it, its annotations land in the same registry tables (`project_file_type_counts`, `project_data_profiles`, etc.) every other survey already writes to, and the existing Results-tab dashboards pick them up with no separate wiring. A `MANUAL_EXTRA_SCOPE_QUESTIONS` override in the generator script gives it ScopedBy links to two real Questions (`"Is this repository actively maintained?"`, `"What does this repository do?"`) since no existing Question's `answering.analysis_ids` references `language_file_classification`/`data_file_profiling` — without at least one ScopedBy link, a Survey Definition is invisible to every phase-scoped candidate panel.

**D3 — Retire the two hardcoded buttons; the generic candidate panel is the only way to run a scouting-tier survey.** `renderScoutingOverview()`'s "Run Scouting Scan" button and the whole "Coarse Profile" card (checkbox, "Refresh coarse profile" button, its own publish button, profiled badge, feedback div) are deleted outright — not hidden, not kept as a fallback. `_loadSurveyPanel('repo', slug, 'scouting', ...)`, already rendered directly below, now carries every scouting-tier survey — Git Statistics Survey, Coarse Profile Survey, and Repo Full Survey — as ordinary candidate cards with `Run →`/`⏱ Schedule` actions. This directly closes complaint (1): there is now exactly one place scouting-tier surveys are listed, and it's the same generic mechanism Discovery already used.

**D4 — One generic "☁ Publish" button per candidate, replacing the per-survey-type hardcoded publish buttons.** `renderSurveyPanel()`'s candidate-card template gains a `☁ Publish` button, scoped to exactly that candidate's own steps: `stepKeys = candidate.steps.map(s => s.re_analysis_step).filter(Boolean)`, wired to the existing `_publishScopedSteps(slug, stepKeys, btn, candidate.display_name)`. `publishScoutingRegistration()` (hardcoded to `['repo_health']`) and `publishProfileFindings()` (hardcoded to the 4 coarse-profile step keys) are deleted — a new Survey Definition now gets a working, correctly-scoped Publish button automatically, no frontend change required. The button only renders for `entityType === 'repo'` candidates with at least one resource-explorer step (`re_analysis_step` is `None`/absent for native/prefect-routed steps, and `_publishScopedSteps`'s route is repo-only today) — omitted rather than shown disabled for database/filesystem candidates. This directly closes complaint (2): every survey type now has exactly one publish action, always scoped to what that survey itself just ran.

**D5 — Rename "Repo Coarse Scout" → "Git Statistics Survey".** `repo_survey_types.csv`'s `RepoCoarseScout` row's `survey_display_name` changed; `qualified_name` (`GovActionProcess::RepoCoarseScout`) deliberately unchanged, so re-running the regenerated doc against Egeria is an in-place *update*, not a new element — confirmed live (GUID identical before/after: `c71cd710-0c33-418b-9b26-005d2d41b350`). "Repo Full Survey" was explicitly left unrenamed (no strong alternative name was proposed, and it's unambiguous as-is). "Coarse Profile Survey" (D2) is new, not a rename.

## A real, live-blocking bug found and fixed along the way

Re-running the renamed Survey Definition's authoring doc against an already-linked process triggered a known, previously-documented Dr.Egeria non-idempotency issue (`Link Next Process Step` duplicates an edge on re-run) — `scripts/reconcile_survey_definition_links.py` exists specifically to clean this up. Running it, however, uncovered a second, independent, real pyegeria bug: `MetadataExpert.delete_related_elements()` can never succeed against a stock Egeria server. `OpenMetadataDeleteRequestBody` (`pyegeria/models/models.py`) declares no `deleteMethod` field at all, and every `PyegeriaModel` is configured `extra='ignore'`, so an explicit `{"deleteMethod": "SOFT_DELETE"}` passed as the raw dict body is silently dropped by pydantic validation before the request ever reaches the server — confirmed by reproducing the identical `OMAG-COMMON-400-032` error with and without the key. The server's own hardcoded default (`LookForLineage`, PascalCase) is itself invalid against the same server's own validation. Logged in `egeria-python`'s `PYEGERIA_ISSUES.md` per this repo's standing convention (never fix egeria-python bugs directly — log and wait for approval) — originally filed as ISSUE-52, renumbered to ISSUE-63 once a stale-branch numbering collision with `origin/main` was caught (main had independently claimed 52-62 for unrelated issues while this branch sat 70 commits behind, never pushed). Update, 2026-08-18: pyegeria 6.0.18.3 fixed the underlying bug class broadly (new `DeleteRelationshipRequestBody.delete_method`, wired into ~15 OMVS modules) but missed `MetadataExpert`'s own two delete methods — issue re-verified as still open for this exact call path; see ISSUE-63 for the current state. Workaround lives entirely in RE's own calling code: `SurveyDefinitionReader.reconcile_step_links()` now bypasses `delete_related_elements()`/pydantic validation for this one call, hitting `MetadataExpert`'s `command_root` + `.../related-elements/{guid}/delete` endpoint directly via its private `_async_make_request()` transport method with a raw dict body. Verified live: the duplicate edge deletes cleanly, the reconciler reports zero duplicates on a follow-up dry run, and `SurveyDefinitionReader().fetch()` against `GovActionProcess::RepoCoarseScout` no longer raises `UnsupportedSurveyDefinitionError` (the branching guard that made "Git Statistics Survey" completely unrunnable until this was fixed).

## Implementation

- **`resource_explorer/surveyors/survey_definition_executor.py`** — `ResourceTypeAdapter.run_batch`, dispatch-loop grouping (D1).
- **`resource_explorer/surveyors/repo_survey_definition_adapter.py`** — `_run_batch()`, registered on `_ADAPTER` (D1).
- **`resource_explorer/surveyors/survey_definition_reader.py`** — `reconcile_step_links()`'s delete workaround (bug fix above).
- **`docs/dr-egeria/repo_survey_types.csv`, `scripts/generate_repo_survey_definition.py`** — Coarse Profile Survey rows + `MANUAL_EXTRA_SCOPE_QUESTIONS` (D2); Git Statistics Survey rename (D5).
- **`docs/dr-egeria/repo-survey-definition-scouting.md`** (regenerated), **`docs/dr-egeria/repo-survey-definition-coarse-profile.md`** (new) — executed live against Egeria.
- **`resource_explorer/web/static/index.html`** — `renderScoutingOverview()` stripped of the two hardcoded action blocks (D3); `renderSurveyPanel()`'s candidate card gains the generic `☁ Publish` button (D4); `runScoutingScan`, `publishScoutingRegistration`, `runProfileScan`, `publishProfileFindings`, and the now-unused `_pollActivityUntilDone` helper deleted as dead code.
