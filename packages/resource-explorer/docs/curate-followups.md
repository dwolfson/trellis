# Curate — scoped follow-ups

Curate is the discoverability/reuse-readiness intent: making a resource easier
to find and more trustworthy to build on. Tags, resource-level feedback, and
curator notes shipped as its first slice (see `web/routes/curate.py`,
`registry.py`'s `resource_tags`/`resource_feedback`/`resource_curator_notes`
tables). Three more capabilities were named in the intent's original
definition but deliberately **not built yet** — each is a real design
question, not a small addition:

## Digital-product evaluation

What does it mean for a resource to be "part of a digital product"? Before
building anything:
- Is this a boolean flag, a workflow with states (candidate → under review →
  certified), or something Egeria already has a native concept for (a
  `DigitalProduct`/`DataProductManager` classification — check pyegeria for
  existing support before inventing an RE-local one)?
- Who has authority to certify a resource as product-ready — any curator, or
  a gated approval step?
- What does "ready" actually require — some minimum tag coverage? Passing
  Assessment analyses? Human sign-off only?

## Sample dataset creation

Generating an actual representative sample of a resource is real, per-type
work, not a generic action:
- Repos: what would a "sample" even mean — a curated file subset, an
  extracted code snippet set?
- Databases: almost certainly the most concrete case — a row-sampled export
  per table, respecting sensitivity/PII constraints from the Enrichment
  Context form (a resource marked `sensitivity: confidential` shouldn't get
  an unreviewed sample generated by default).
- Filesystems: similar to repos — likely a representative file subset.
- Where do samples live — Egeria as a distinct asset, or local storage with
  just a pointer/manifest in the catalog?

## Addressing quality issues

Surveys already surface quality problems as RFAs (RequestForAction
annotations) — e.g. Security Scan, Index Health, Privilege Audit findings.
Two different things could be meant here, and they lead to different designs:
- **Curator remediation of existing RFAs** — closing them out is already
  possible via the RFA drawer (`PATCH /api/activity/rfas/{id}`, `completed`
  status). If this is what's meant, it may need nothing new — just better
  visibility of open quality-related RFAs from within Curate itself (e.g. a
  resource-scoped RFA view embedded in the Curate pane, reusing
  `GET /api/activity/rfas?entity_slug=...`, which already supports this
  filter).
- **A distinct quality-remediation workflow** — e.g. tracking a fix as
  in-progress, linking it to an actual code/schema change, verification that
  the issue is actually resolved (re-running the analysis that found it) —
  a genuinely new lifecycle, not just an RFA status change.

Which of these two is intended needs to be settled before scoping further.
