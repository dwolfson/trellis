### What the numbers say
1. **The re-base alone fixes the mechanics but barely moves the answers** (0% → 3%). It ends the baseline's
   crashes (8/30 died in `_generate_report_spec_md`: the LLM returns a list where a string is joined), wrong
   find methods (glossaries listed for "terms", Projects for products, `find_projects` for Assets) and
   invented methods. But EA's prompt still picks wrong or vague types, and nothing applies the condition.
   Grounding turns a wrong guess into an honest error, not a right answer.
2. **The fixes do most of the lift on the 30** (3% → 50%), mainly the status and sort conditions and
   asking on ambiguous requests.
3. **The hold-out gap is the main finding: 50% on the 30 vs 17% on the 12.** Most hold-out questions ask
   about **related elements or aggregates**: term counts per glossary, a spec's structures, a blueprint's
   components, a collection's member counts, a team's leader, a project's manager. A spec over one type's own
   attributes can't express those, so they score 1. The 30 had more status/sort questions, which the
   conditions solve. Neither set reaches 70%. The gap says the tuning fits the kind of question in the 30
   better than questions in general.
4. **Ambiguity:** 5/5 and 2/2 asked. But H10 ("Which sites or locations…") is a clear question that was
   asked anyway: its named-type check didn't recognise "sites or locations".

## Other findings
- **Dr.Egeria has no `Create Column` command** (offline parse: "No specification found for command: Create
  Column"). Every document EA's elicitor writes today should fail Dr.Egeria validate. pyegeria's serializer
  writes the columns inside the `Microflow` instead.
- **pyegeria's attribute check is loose:** it accepts any column key some registered spec uses, for any type
  (EA's camelCase `qualifiedName` on Project passes). The harness also records a strict check; both were 0

## The authoring-API functions the re-base needed (for pyegeria-sd-dcat, via the Coordinator)
Used as is:
- `pyegeria.authoring.SpecDraft(label, format_set)`
- `validate(draft, client=None, *, run=None) -> ValidationResult`
- `serialize(draft, *, title=None) -> str`
- `preview(draft, *, client, max_rows, params) -> {"result","capped","shown","notes"}`
- `inprocess_runner(client) -> run(md, directive)`
- `pyegeria.authoring.serialize.parsed_attributes(md)`
- `pyegeria.view.microflow.parse_microflow`, `microflow_to_format_set(mf, label=, heading=, description=, target_type=)`
- `pyegeria.view.report_spec_publish.build_publish_document(label, fs, *, folders, visibility, zones, held, restricted)`
- `build_withdraw_document(label, folders, *, allowed, allowed_words)`, `PublishRefused`, `summarise`

Needed, but reached into private names or rebuilt in EA (asks for the API):
1. **`load(markdown) -> SpecDraft`**, the inverse of `serialize` (EA rebuilt it from `parsed_attributes`
   + microflow).
2. **A public type catalog:**
   - `type_attributes(type)` is public;
   - `DERIVED_KEYS`, `_registry_columns_and_types`, `_snake` are private and used;
   - plus `resolve_type(name)` (spacing, aliases), `attribute_menu(type) -> [(key, label)]`, and
     `find_action(type) -> {function, spec_params}` from the type's registered spec. ~180 lines in EA today.
3. **validate:** check the find method fits the target type; a strict mode for column keys (the type's
   own attributes only).
4. **preview params:** `start_from` etc. pass through, but `page_size` is overridden by `max_rows`
   (fine); say in the docstring which params it takes.

## Recommendation (for the owner, via the read-back)
- **Re-base: yes, on its own terms.**
  - It removes EA's crash path, invented find methods, its own parser and markdown generator, and the
    publish duplicates.
  - It's measurably more honest: a wrong type is an error, unknown columns are named.
  - Ship it with the grounding moved into pyegeria (asks 1–2) and the read-back's sample re-run live.
- **Don't expect the re-base to make EA answer questions.** That comes from the conversation, and even
  with the fixes the hold-out is 17%.
  - The 70% target needs specs that follow **relationships and aggregates** (members, components, roles,
    counts). That's pyegeria's spec model plus analytic routines, i.e. Studio/API work, not EA prompt
    tuning.
  - Prototype it next as a small set of relationship-aware column templates, measured on a fresh hold-out.
- **Retire next:** the elicitor's markdown and doc code once V2 is the path; the B6 page in favour of
  "promote" in chat + Studio (D18 unchanged).
- **Before any number here is final: the live run** (needs the owner's yes in this session). It gives
  criterion 1's "runs", Dr.Egeria validate, row counts, the real latency, and any score drops for empty
  results.
